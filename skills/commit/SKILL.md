# Git Commit

Follow these steps every time you create a commit. No exceptions.

## Step 1: Gather context

Run in parallel:
- `git status` — modified, staged, and untracked files
- `git diff --cached` — what's already staged
- `git diff` — unstaged changes
- `git log --oneline -5` — recent message style to match

If `git diff --cached` is empty and `git diff` is also empty, abort — nothing to commit.

## Step 2: Stage files

- Stage files individually by name: `git add <file1> <file2> ...`
- **Never** use `git add -A`, `git add .`, or `git add --all`
- **Never** stage files that may contain secrets: `.env`, `credentials.*`, `*token*`, `*.pem`
- If unsure whether a file should be committed, ask the user

## Step 3: Review the diff

Run `git diff --cached --stat` to confirm what will be committed. If something looks wrong, unstage it before proceeding.

## Step 4: Write the commit message

Study the recent `git log` output and match the repository's style.

**Message rules:**
- One-line summary in imperative mood ("add", "fix", "update" — not "added", "fixed")
- Max 72 characters for the summary line
- Optional body after a blank line — explain **why**, not what (the diff shows the what)
- Bullet points for multi-file changes when context helps

**Absolutely forbidden in commit messages:**
- `Co-Authored-By` trailers of any kind
- Any mention of Claude, Anthropic, AI, LLM, or assistant
- `Generated by` or `assisted by` lines
- Emoji

## Step 5: Commit

Use a HEREDOC to preserve formatting:

```bash
git commit -m "$(cat <<'EOF'
summary line here

- optional body point
- another point
EOF
)"
```

## Step 6: Verify

Run `git status` to confirm the commit succeeded. Report the result briefly — do not summarize what you just did, the user can read the diff.
